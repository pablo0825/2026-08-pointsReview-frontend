## 2. 系統主要流程

**已確認**

1. 學生開啟公開申請頁。
2. 填寫學生及申請資料。
3. 選擇指導老師。
4. 上傳附件。
5. 送出申請。
6. 指導老師登入。
7. 指導老師完成簽名或確認。
8. 承辦人登入。
9. 承辦人核准申請。
10. 核准後產生正式學生點數。
11. 公開點數頁顯示結果。

退件、拒絕、補件、撤回等例外流程仍待討論。

## 3. 學生申請方式與身分驗證

**已確認**

- 申請頁為公開頁面，學生不需要登入即可填寫申請。
- 第一版不串接學校 SSO。
- 第一版不進行 Email 驗證。
- 申請資料屬於學生自行申報。
- 送件後由已登入的指導老師確認，再交由承辦人審核資料與附件。
- 承辦人核准後才正式產生學生點數。
- 未來如有更高的身分驗證需求，再評估串接學校 SSO 或加入 Email 驗證。

## 4. 申請人與參與者

### 4.1 單人及多人申請

**已確認**

- 系統支援單人及多人申請。
- 每份申請至少包含一位參與者。
- 申請人必須是該份申請的其中一位參與者。
- 每份申請必須且只能指定一位參與者為申請人。

### 4.2 申請人資料

**已確認**

申請人需要提供：

- 姓名
- Email
- 電話

其中 Email 與電話用於接收通知及後續聯絡，且只需要由申請人提供。

### 4.3 參與者資料

**已確認**

每位參與者需要提供：

- 姓名（`studentName`）
- 學號（`studentNumber`）
- 年級（`grade`）
- 班級（`classNumber`）
- 申請點數（`requestedPoints`）
- 是否為申請人（`isApplicant`）

學號是學生點數紀錄的主要識別資料。

### 4.4 申請人的選擇方式

**暫定**

- 使用者先建立所有參與者，再從參與者清單中指定一位申請人。
- 表單不另外要求使用者重複輸入申請人姓名。
- `applicant.name` 直接使用被指定參與者的 `studentName`。
- 此設計可避免申請人姓名與參與者姓名因錯字、空格或格式不同而不一致。

## 5. 學年度

**已確認**

- 學年度在前端表單中是整份申請的共用欄位。
- 使用者只需要選擇或輸入一次學年度。
- API 傳送時，前端將共用學年度複製到每位參與者的 `academicYear`。
- `academicYear` 使用字串，例如 `"114"`。
- 第一版不考慮同一份申請包含不同學年度。
- 如需申請不同學年度的點數，原則上應拆成不同申請。

## 7. 點數

**已確認**

- `requestedPoints` 位於每位參與者資料中。
- API 使用十進位字串，例如 `"10.00"`。
- 學生送出申請後不會立即產生正式點數。
- 指導老師確認且承辦人核准後，才產生正式學生點數。

### 7.1 競賽

**已確認**

- `per_person`：每位參與者的申請點數由適用規則決定，所有人取得相同的固定點數。
- `shared_total`：申請人可分配各參與者的申請點數，但所有參與者的點數合計必須等於規則總點數。
- 競賽點數以 `0.5` 點為最小分配單位。
- `shared_total` 只有一位參與者時，前端直接將全部規則點數帶入該參與者。
- `shared_total` 有多位參與者時，不自動平均分配，由申請人逐一分配每位參與者的點數。
- 多人分配控制以 `0.5` 點為步進，前端只協助顯示與驗證，不代替申請人決定分配結果。
- 已進行分配後新增參與者時，保留其他參與者的既有點數，並先為新參與者帶入最低 `0.5` 點。
- 已進行分配後移除參與者時，保留其他參與者的既有點數，被移除者原有點數回到尚未分配點數。
- 增減參與者造成點數合計不符時，前端應提示申請人重新調整，完成平衡前不得送件。
- 每位參與者的申請點數必須大於 `0`；在 `0.5` 點精度下，每位參與者至少分配 `0.5` 點。
- `shared_total` 的實際參與人數上限須同時受到規則總點數限制，計算方式為 `FLOOR(規則總點數 / 0.5)`。
- 前端允許的參與人數上限，取申請類型人數規則上限與點數可分配人數上限兩者的較小值。
- 例如規則總點數為 `1` 點時，最多只能有 `2` 位參與者，即使競賽類型的一般人數上限為 `10` 人。
- 達到實際人數上限後，前端應停用新增參與者功能並顯示原因。
- 前端應顯示已分配點數、規則總點數及尚未分配點數。
- 前端送出前應驗證每筆點數皆為 `0.5` 的倍數，且 `shared_total` 的合計符合規則總點數。
- 後端仍是點數規則與合計驗證的最終可信來源。
- 第一版獎項只開放 `participation`、`finalist`、`honorable_mention`、`third_place`、`second_place`、`first_place`。
- 第一版不提供 `other_award`（其他獎項），前端不得顯示該選項，送件 Schema 與後端也不應接受該值。
- 若未來要開放其他獎項，必須先定義其點數規則及審核方式。
- 競賽日期 `competitionDate` 代表競賽完成或結果公布日期，且為必填欄位。
- `competitionDate` 不得晚於 `Asia/Taipei` 的今天；前端應限制未來日期，後端仍須進行最終驗證。

### 7.2 展覽申請

**已確認**

- 中文申請類型名稱使用「展覽申請」，同時涵蓋校內展與校外展。
- API 與程式碼中的申請類型識別值使用 `exhibition`，不再使用 `external_exhibition`。
- 此識別值屬於前後端契約；後端 Enum、資料庫限制、API 文件及測試須同步調整。
- 展覽申請點數不接受規定範圍內的任意小數。
- `fan_work`（同人作品）：每位參與者只能申請 `0.5` 或 `1` 點。
- `project_work`（專題作品）：每位參與者只能申請 `1` 或 `2` 點。
- 前端應使用下拉選單或單選按鈕，不提供自由輸入。
- 申請前台的公開規則 API 使用 `allowedPointsPerPerson` 回傳離散選項，例如 `["0.50", "1.00"]`。
- 前端選項應直接依公開 API 的 `allowedPointsPerPerson` 產生，不應只在程式碼中寫死。
- 公開 API 不向申請前端提供 `minimumPointsPerPerson` 與 `maximumPointsPerPerson`。
- 管理端規則 API 暫時保留 `minimumPointsPerPerson` 與 `maximumPointsPerPerson`，由後端轉換成公開 API 的端點選項。
- 後端仍須驗證每位參與者的申請點數是否為該展覽類型允許的離散值。
- 只驗證最低與最高點數範圍並不足夠，例如同人作品的 `0.75` 即使位於 `0.5` 至 `1` 之間，仍屬無效值。
- 展覽開始日期 `startDate` 與結束日期 `endDate` 必填。
- `endDate` 不得早於 `startDate`。
- 學生只能在展覽結束後申請點數，因此 `endDate` 不得晚於 `Asia/Taipei` 的今天。
- 前端應限制無效日期並提供即時提示，後端仍須進行最終日期驗證。

### 7.3 參與計畫

**已確認**

- 一份參與計畫申請可包含多筆逐月薪資明細。
- 每筆薪資明細包含薪資月份與薪資金額。
- 同一份計畫申請中的薪資月份不得重複。
- 前端新增或修改薪資月份時，應即時檢查並阻止重複月份。
- 後端仍須驗證同一份計畫申請內薪資月份的唯一性。
- 每筆薪資金額以新臺幣元為單位，必須是大於 `0` 的整數。
- 薪資金額不接受 `0`、負數或小數；金額為 `0` 的月份不需建立明細。
- 薪資月份只能選擇當月或過去月份，不允許未來月份。
- 前端月份選擇器應以 `Asia/Taipei` 的目前月份設定可選上限，後端仍須進行最終日期驗證。
- `salaryMonth` 傳送及保存時使用該月份第一天，例如 `2026-08-01`。
- 前端應顯示薪資合計與依目前規則計算的預估點數，最終點數由後端計算。
- 薪資合計未滿新臺幣 `1,000` 元時計算結果為 `0.00` 點，不符合參與者申請點數必須大於 `0` 的規則。
- 預估點數為 `0.00` 時，前端應顯示「薪資總額未達可申請點數門檻」並禁止送件。
- 後端仍須拒絕參與計畫的零點申請。

### 7.4 證照

**已確認**

- 一份證照申請只包含一位參與者，且該參與者必須是申請人。
- 每張證照的申請點數由系統依規則自動設定，不由申請人手動輸入。
- 證照日期 `issuedDate` 必填，且不得晚於 `Asia/Taipei` 的今天。
- 前端日期選擇器應禁止選擇未來日期，後端仍須進行最終日期驗證。
- 同一位學生禁止使用相同證照重複申請。
- 相同證照暫以 `studentNumber` 與 `certificateNumber` 的組合判斷。
- 相同證照若已有審核中、補件中或已核准的申請，禁止建立新申請。
- 相同證照先前的申請若已因申請人要求結束或最終不核准，允許重新申請。
- 退回補件時應修改並重新送出原申請，不得另建重複申請。
- 重複證照屬於跨申請的歷史資料驗證，必須由後端進行最終檢查。
- 前端收到重複證照錯誤時，應顯示可理解的欄位或表單層級訊息，不只顯示一般送件失敗。
- 每位學生在整個在學期間的證照類累積點數上限由有效規則決定；超過上限時不可部分核准。

### 7.5 申請點數與核定點數

**已確認**

- 每位參與者的學生申請點數保存於 `requestedPoints`，承辦人最終核定點數另存於 `approvedPoints`。
- `approvedPoints` 必須大於 `0`，且必須符合該申請類型的有效規則；承辦人不得核准 `0` 點。
- 若某位參與者不應取得點數，代表申請事實或參與者資料需要修正，承辦人應要求補件或最終不核准，不建立零點核准紀錄。
- 後端流程文件中「承辦人最低可調整為 0 點」的舊敘述與本決策衝突，需同步移除或修正。
- 核准後只將 `approvedPoints` 寫入學生點數流水帳，原始 `requestedPoints` 必須保留供審核追溯。
- 競賽：承辦人可修正競賽等級，再依適用規則核定點數；不得任意輸入規則以外的點數。
- 競賽採 `shared_total` 時，核定後每位參與者點數仍須以 `0.5` 為單位、每人大於 `0`，且合計等於核定規則總點數。
- 展覽申請：承辦人只能從該展覽類型的 `allowedPointsPerPerson` 中核定每位參與者點數。
- 參與計畫：承辦人不得直接修改系統計算點數；薪資資料有誤時應退回補件，由系統依修正後的薪資重新計算。
- 證照：依有效規則固定核定點數，不允許部分核准或任意調整；超過學生證照類累積上限時整筆不可核准。

## 9. 指導老師選擇

**已確認**

- 公開申請表透過 `GET /public/advisors` 取得目前可選擇的指導老師。
- API 只回傳老師資料與關聯帳號皆為啟用狀態，且帳號已完成首次啟用的老師。
- API 不回傳老師的 Email、員工編號或登入帳號。
- 第一版 endpoint 不提供姓名關鍵字、分頁或後端搜尋，每次回傳全部可選老師。
- 前端使用可搜尋下拉選單，並在本機同時依姓名、職稱及系所篩選。
- 下拉選單顯示格式為「姓名｜職稱｜系所」，例如「王大明｜專任副教授｜視覺傳達設計系」。
- `isDirector` 不顯示於公開老師選單，也不參與搜尋、排序或選擇邏輯；主任身分不影響學生選擇指導老師。
- 前端選取老師後，正式送件只傳送並保存 `advisor.id`，不傳送前端組合的顯示文字。
- 未來老師資料量明顯增加時，再評估後端 `keyword` 搜尋與分頁；第一版不新增搜尋 API。

## 10. 後台登入

**已確認**

- 指導老師、承辦人與管理員共用同一個登入頁面，建議路由為 `/login`。
- 使用者以 Email 與密碼呼叫 `POST /auth/login`。
- 登入成功後由後端設定 HttpOnly Session Cookie；前端不得保存密碼或 Session Token。
- 前端透過 `GET /auth/me` 取得目前使用者、角色及權限，並依 `role` 導向對應首頁。
- 需要修改狀態的 API，前端須取得 CSRF Token 並以 `X-CSRF-Token` header 傳送。
- 指導老師從 Email 待簽連結進入時，前端須保留原始目標；登入成功後返回指定申請的簽核頁，而不是導向一般首頁。
- 已登入但角色或資料權限不符時顯示 403 頁面，不導向其他角色頁面。

## 11. 指導老師簽核

### 11.1 手寫簽名

**已確認**

- 指導老師同意申請時，必須在簽核頁使用手寫簽名板完成簽名。
- 簽名板須支援滑鼠、觸控筆及行動裝置觸控操作。
- 提供清除及重新簽名功能。
- 第一版不開放上傳既有簽名圖片，避免誤傳其他檔案或使用不明來源簽名。
- 空白簽名不得送出，前端須檢查簽名板確實有筆跡。
- 前端將簽名板輸出為 PNG，使用 `multipart/form-data` 的 `signature` 欄位送出。
- PNG 最大 `1 MB`，圖片尺寸最大 `1600 x 800` pixels；前端送出前應驗證，後端仍須進行最終驗證。
- 同意時一併傳送 `confirmVersionNumber`，確保老師簽署的是目前檢視的申請版本。
- 老師必須先檢視申請資料及附件，才能完成同意與簽名操作。

### 11.2 簽名確認與限制使用

**已確認**

- 不使用獨立的確認核取方塊，避免形成只有形式上的勾選操作。
- 簽名區上方顯示：「此簽名僅用於本次點數申請，並表示您已確認申請內容與實際指導情形相符。」
- 主要操作按鈕使用明確文字「簽名並同意送交審核」。
- 正式送出前顯示確認視窗，降低誤觸送出的風險。
- 最終保存及顯示的簽名圖片應包含「僅供本次點數審核申請使用」浮水印。
- 簽名圖片應標示申請編號、申請版本及簽署時間，限制簽名只能用於該次申請。
- 浮水印與申請資訊應由後端合成，不能只信任前端輸出的圖片。
- 前端只在當次簽署操作中暫存原始簽名，不寫入 Local Storage、Session Storage 或其他持久化瀏覽器儲存；送出成功或離開頁面時應清除。
- 前端不得提供公開簽名網址；簽名檔只可透過具權限的私有檔案 API 查看。
- 後端合成、保存原始或浮水印簽名的具體方式，需在後端專案同步確認並更新 API 契約。

### 11.3 拒絕申請

**已確認**

- 指導老師只能在簽核期限內執行同意或拒絕。
- 老師拒絕申請時不需要簽名，但拒絕原因必填且不可只有空白。
- 拒絕送出前顯示確認視窗，清楚提示拒絕後申請將結束且無法補件。
- 拒絕後申請進入終止狀態 `rejected`，並記錄結束時間及拒絕操作。
- 系統通知申請人拒絕結果與原因。
- 老師端第一版不提供退回補件；若內容需要修正，老師拒絕後由學生建立新申請。
- 承辦人階段才提供正式的退回補件流程。

### 11.4 簽核期限與提醒

**已確認**

- 指導老師簽核期限預設為申請送出或補件重新提交後 `168` 小時（7 天）。
- 申請進入 `pending_advisor` 後立即寄送簽核通知。
- 第一次提醒於期限前 `72` 小時寄送。
- 第二次提醒於期限前 `24` 小時寄送。
- 第三次提醒於期限前 `4` 小時寄送。
- 超過期限仍未簽名或拒絕時，系統將申請轉為 `rejected` 並通知申請人。
- 第一版不提供指導老師簽核期限延長功能。
- 老師待簽列表及詳情頁顯示明確截止時間；接近期限時使用醒目但不干擾閱讀的警示樣式。

## 12. 附件

### 12.1 檔案與數量限制

**已確認**

- 第一版允許 PDF、JPEG 與 PNG。
- 每個檔案最大 `5 MB`。
- 每份申請最多 `10` 個附件。
- 第一版不接受 ZIP、RAR 或其他壓縮檔。
- 附件與申請資料同一次送出，第一版不提供送件前暫存附件。
- 附件為私有檔案，不提供公開靜態網址。
- 前端可預先檢查副檔名、瀏覽器回報的 MIME type、檔案大小及數量；後端仍須驗證實際檔案內容。

### 12.2 各類型最低附件要求

**已確認**

- 競賽：`participation_proof`（參賽證明）或 `finalist_or_award_certificate`（入圍或獎狀）至少一份。
- 參與計畫：`salary_proof`（薪資證明或薪資截圖）至少一份。
- 證照：`certificate_copy`（證照影本）至少一份。
- 展覽申請：`exhibition_photo`（參加展覽照片）至少一份。

### 12.3 附件 Metadata

**已確認**

每個附件送件時包含：

- `clientFileKey`：由前端產生，用來將 metadata 與 multipart 檔案欄位配對，不顯示給使用者，也不由後端保存。
- `attachmentType`：使用者必須選擇的附件分類。
- `attachmentTypeOther`：只有選擇 `other` 時必填；其他分類時必須為 `null`。
- `description`：附件補充說明，可選填。

前端不要求使用者手動輸入原始檔名、MIME type 或檔案大小；這些資料由所選檔案及後端驗證結果取得。

### 12.4 前端內容提示與分類篩選

**已確認**

- 前端只提供附件應包含內容的提示，不嘗試自動判斷證明內容是否真實或完整；實際有效性由指導老師與承辦人確認。
- 競賽證明提示：應能辨識競賽名稱、參與者或團隊、獎項或參賽結果。
- 薪資證明提示：應能辨識領薪月份、薪資金額及領薪人。
- 證照影本提示：應能辨識姓名、證照名稱、發照單位、證照編號及日期。
- 展覽照片提示：應能辨識作品或參展情形，可另附海報或活動資訊佐證。
- 前端依申請類型篩選相關附件分類，避免顯示無關選項。
- 競賽可選：`competition_rules`、`competition_poster`、`official_website_screenshot`、`official_document`、`participation_proof`、`finalist_or_award_certificate`、`other`。
- 參與計畫可選：`salary_proof`、`official_document`、`other`。
- 證照可選：`certificate_copy`、`other`。
- 展覽申請可選：`exhibition_photo`、`exhibition_poster`、`official_document`、`other`。

## 13. 承辦人審核

### 13.1 要求補件

**已確認**

- 承辦人只能對審核中的申請要求補件，補件原因必填且不可只有空白。
- 要求補件後申請進入 `needs_revision`，由系統寄送具有期限的補件連結給申請人。
- 學生透過補件連結修改原申請並重新送出；第一版不允許在補件時變更 `applicationType` 或 `advisorId`。
- 補件頁的指導老師欄位應顯示原老師但不可編輯，前端送出時沿用原 `advisorId`；後端也必須拒絕變更。
- 學生若要更換指導老師，只能放棄原流程並建立新申請；不得利用補件連結轉交其他老師。
- 後端現有補件 API 文件允許改變 `advisorId`，與本決策衝突，後端契約與驗證需同步修改。
- 重新送出時建立新的申請版本，不覆蓋或刪除舊版本。
- 原指導老師的舊簽名只綁定舊版本，因此補件重新送出後必須標記失效。
- 補件重新送出後，申請回到 `pending_advisor`，由指導老師重新檢視新版本並再次簽名，再回到承辦人審核。
- 學生不得繞過老師重新簽名直接將補件版本送回承辦人。
- 承辦人可在補件連結尚未失效時延長期限，延長原因必填。
- 補件期限屆滿仍未重新送出時，申請由系統轉為終止狀態 `rejected`。
- 所有舊版本、失效簽名、補件原因、重新送出及期限異動皆保留供稽核。

### 13.2 最終不核准

**已確認**

- 承辦人最終不核准時，原因必填且不可只有空白。
- 送出前顯示確認視窗，說明不核准會立即結束申請且無法再補件或恢復。
- 不核准後申請進入終止狀態 `rejected`，並記錄結束時間及審核操作。
- 不核准的申請不產生任何學生點數。
- 系統通知申請人不核准結果及原因。
- 原申請不能再修改、補件或恢復；學生若仍需申請，必須建立新申請。
- 若資料仍可修正，承辦人應使用「要求補件」，不應使用「不核准」。

## 14. 學生送件後操作

### 14.1 進度查詢

**已確認**

- 第一版不提供學生主動查詢申請進度的公開頁面或 API。
- 送件成功頁顯示 `publicId` 作為申請編號，並提醒學生保存。
- 第一版以 Email 通知申請狀態異動、補件要求、核准及拒絕結果。
- 第二版再評估提供使用獨立高強度 Token 的唯讀進度查詢連結。
- 第二版查詢 Token 必須與有期限且可編輯的補件 Token 分開，不得使用查詢連結修改申請。

### 14.2 撤回申請

**已確認**

- 第一版不提供學生自行撤回申請的前端功能或公開 API。
- 申請尚待老師簽名時，學生須聯絡指導老師，由老師以「申請人要求撤回」等明確原因拒絕申請。
- 申請已進入承辦人審核時，學生須聯絡承辦人，由承辦人以相同原因最終不核准。
- 系統保留拒絕或不核准原因及完整操作紀錄。
- 第二版若導入安全查詢 Token，再評估正式的 `withdrawn` 狀態與學生自助撤回操作。

## 15. 公開學生點數頁

### 15.1 初始查詢行為

- 使用者必須先同時選擇年級與班級，或輸入姓名／學號關鍵字，才顯示查詢結果。

- 關鍵字、年級與班級可以同時使用，以進一步縮小查詢結果。

### 15.2 顯示欄位

- 顯示學年度、年級、班級、競賽點數、參與計畫點數、證照點數、展覽點數、總點數及更新時間。
- 因申請類型已由 `external_exhibition` 改為 `exhibition`，公開 Response 欄位應使用 `exhibitionPoints`，不再使用 `externalExhibitionPoints`；後端契約需同步修改。

## 16. 後台角色與權限

### 16.1 承辦人共用案件池

**已確認**

- 系統可存在多位承辦人。
- 第一版不提供案件指派、案件認領或依系所隔離功能。
- 所有啟用中的承辦人都能查看全部待審、補件中及歷史案件。
- 任一具有權限的承辦人都能要求補件、延長補件期限、核准或不核准案件。
- 每次操作必須保存實際執行的承辦人及操作時間。
- 後端在最終審核操作時必須鎖定目標案件並重新檢查狀態與版本，避免多位承辦人同時操作造成重複核准或狀態覆蓋。
- 若未來承辦人數或系所分工增加，再評估案件指派與資料範圍隔離。

### 16.2 管理員權限

**已確認**

- 第一版同一時間只允許一位啟用中的管理員。
- 管理員可查看所有申請、版本、附件、簽名及審核操作紀錄。
- 管理員可管理使用者帳號、指導老師、主任、點數規則、人數規則及申請說明。
- 管理員可查詢學生點數流水帳。
- 管理員不得要求補件、核准或不核准申請，不能代替承辦人執行審核。
- 只有承辦人能執行補件與最終審核操作，維持規則管理與個案審核的權責分離。

## 17. 稽核與審核歷史

**已確認**

- 申請流程狀態與操作使用 `application_review_actions` 保存，包括送件、老師同意或拒絕、要求補件、重新送出、核准、不核准及逾期等事件。
- 老師、承辦人及管理員的申請詳情頁，依各自資料權限以時間軸顯示申請審核歷史。
- 老師只能查看自己負責申請範圍內的歷史；承辦人可查看所有審核案件；管理員可唯讀查看所有申請歷史。
- 系統級 `audit_logs` 記錄帳號、老師、主任、規則等管理異動，以及附件與簽名等敏感檔案的查看操作。
- 第一版後端必須寫入 `audit_logs`，但前端不製作系統稽核紀錄查詢頁。
- 稽核紀錄的篩選、搜尋與匯出介面列入第二版評估。

## 18. API 錯誤處理

**已確認**

- API 錯誤使用穩定的 `code` 與可讀的 `message`；前端不得直接顯示 SQL、Stack Trace 或未知後端技術訊息。
- `422 validation_failed`：將 `fields[].path` 對應至 React Hook Form 欄位，顯示欄位訊息並聚焦第一個錯誤。
- `400` 業務規則錯誤：在表單或操作區頂部顯示後端訊息；能可靠對應欄位時同步標示。
- `401`：清除目前登入者及權限快取，導向登入頁並保留安全的返回網址。
- `403`：顯示權限不足頁面。
- `404`：顯示資料不存在、無權揭露或連結已失效的適當訊息。
- `409`：提示資料或申請狀態已被其他人更新，重新取得最新資料後再操作。
- `429`：顯示操作過於頻繁，保留已填資料並提示稍後重試。
- `500` 或網路錯誤：顯示一般錯誤訊息及重試按鈕，不清除使用者已填資料。
- 所有 mutation 失敗時保留表單與簽核輸入；原始手寫簽名只保留在目前頁面的記憶體中，不持久化到瀏覽器儲存。

## 19. 申請狀態與轉移

**已確認**

第一版狀態：

| 狀態 | 說明 |
| --- | --- |
| `pending_advisor` | 等待指導老師簽名或拒絕 |
| `under_review` | 指導老師已同意，等待承辦人審核 |
| `needs_revision` | 承辦人已要求補件，等待申請人重新提交 |
| `approved` | 已核准並建立點數流水帳，終止狀態 |
| `rejected` | 已拒絕、逾期作廢或依申請人要求結束，終止狀態 |

狀態轉移：

```text
建立申請 -> pending_advisor

pending_advisor -> under_review   老師簽名同意
pending_advisor -> rejected       老師拒絕或簽核逾期

under_review -> needs_revision    承辦人要求補件
under_review -> approved          承辦人核准
under_review -> rejected          承辦人最終不核准

needs_revision -> pending_advisor 學生完成補件並建立新版本
needs_revision -> rejected        補件逾期、承辦人最終不核准或依申請人要求結束
```

- `approved` 與 `rejected` 為終止狀態，進入時必須記錄 `closedAt`，不得再修改或恢復。
- `pending_advisor`、`under_review` 與 `needs_revision` 的 `closedAt` 必須為 `null`。
- 補件後的新版本必須重新經過老師簽名，不得直接回到 `under_review`。
- 第一版沒有 `draft`、`withdrawn` 或學生登入後自行編輯狀態。
- 所有狀態轉移都必須由後端在 Transaction 內重新驗證目前狀態與版本，前端顯示不能作為操作依據。

## 22. 承辦人頁面

### 22.1 審核工作區與狀態頁籤

**已確認**

```text
/reviewer/applications/review
/reviewer/applications/review/:publicId
/reviewer/applications/history
/reviewer/applications/history/:publicId
```

- 審核工作區分為「待審核」與「補件中」兩個頁籤。
- 「待審核」使用 `GET /reviewer/applications/review?status=under_review`。
- 「補件中」使用 `GET /reviewer/applications/review?status=needs_revision`。
- 省略 `status` 時維持回傳 `under_review` 與 `needs_revision` 兩種未結案案件，保留通用工作佇列與向後相容性；前端頁籤固定明確傳送 `status`。
- `status` 篩選必須由後端搭配分頁執行，前端不得只對單頁結果做本機篩選。
- 前端將 `status` 納入 TanStack Query Key，兩個頁籤各自保留分頁與篩選狀態。
- 審核操作改變狀態後，前端須使受影響的兩個工作佇列及歷史列表快取失效並重新取得。
- API Response 項目仍須包含實際 `status`，前端不能只根據目前頁籤推定狀態。
- 不合法的 `status` 值由後端回傳 `422 validation_failed`。

待審核列表顯示申請編號、申請類型、申請人、申請總點數、指導老師、老師簽署時間、最近更新時間及查看審核操作。

補件中列表另外顯示補件原因摘要、補件截止時間、即將到期或已逾期標記，以及延長期限操作。

### 22.2 審核詳情頁

**已確認**

詳情頁依序呈現：

1. 申請摘要：申請編號、申請類型、目前狀態、目前版本、送件時間及最近更新時間。
2. 申請人與參與者：學年度、姓名、學號、年級、班級、申請點數及申請人聯絡資料。
3. 類型專屬內容：競賽、參與計畫、證照或展覽的事實資料。
4. 點數審核：學生申請點數、適用規則、承辦人核定點數，以及調整原因。
5. 附件：依附件分類預覽或下載私有檔案。
6. 指導老師簽名：老師、簽署時間、簽署版本及具有浮水印的簽名圖片。
7. 版本與審核時間軸：補件原因、版本摘要、老師簽名、狀態轉移及操作者。
8. 操作區：依狀態提供要求補件、最終不核准、延長補件期限或核准申請。

- 手機版改為單欄依序排列，操作按鈕置於頁面底部且不得遮住內容。
- 承辦人核准前應能在同一畫面比對學生申請值、規則值與核定值。
- 未調整核准資料時，不要求填寫調整原因；任何核定資料或點數調整都必須填寫原因。

### 22.3 補件中案件操作

**已確認**

- `needs_revision` 狀態可查看補件原因、期限、版本及完整歷史。
- 承辦人可延長仍有效的補件期限，延長原因必填。
- 承辦人可填寫必填原因後執行最終不核准，包括依申請人要求結束申請。
- `needs_revision` 不允許直接核准，因為學生尚未完成補件且新版本尚未經老師重新簽名。
- `needs_revision` 不允許再次要求補件；必須等待學生重新提交、延長期限或最終不核准。
- 狀態機加入人工轉移 `needs_revision -> rejected`，並保留原本補件逾期的系統自動轉移。

## 25. API 契約與前端型別

**已確認**

- 後端第一版尚未提供正式 OpenAPI；前端使用 Zod 定義 API Request 與 Response Schema。
- TypeScript API 型別由 `z.infer` 從 Zod Schema 產生，不另外維護重複的手寫型別。
- 表單 Schema／型別與 API Schema／型別分開，避免 UI 結構直接綁定後端 payload。
- 使用明確 Mapper 將五步表單狀態轉換成正式 API payload，並集中處理共用學年度、申請人與參與者等資料轉換。
- API Response 在執行時經 Zod 驗證；契約不符時顯示安全的一般錯誤，不將原始敏感資料或內部解析訊息呈現給使用者。
- 日期在 API 邊界維持 ISO 字串，只有在顯示或表單互動時轉換。
- 點數在 API 邊界維持兩位小數字串，例如 `"10.00"`。
- 前端加總及比較點數時轉成整數最小單位，避免直接使用 JavaScript 浮點數；顯示與送件時再轉回兩位小數字串。
- 共用 API Client 統一處理 HttpOnly Cookie 所需的 credentials、CSRF Header、JSON／multipart、成功解析及穩定錯誤格式。
- TanStack Query Key 集中管理，並包含角色、資源、狀態、篩選及分頁等會影響結果的參數。
- 第一版不直接 import 或複製後端原始 TypeScript 型別；未來後端產出正式 OpenAPI 後，再評估型別或 Client 產生工具。

## 26. 測試策略

**已確認**

### 26.1 Vitest 單元測試

- 測試不依賴畫面的純函式與業務規則，包含點數字串轉換、整數最小單位運算、共享點數合計、動態人數上限、薪資換點、日期及月份驗證。
- 測試四種申請的表單資料轉 API Payload Mapper，以及 API 欄位錯誤映射。
- 單元測試應快速執行，作為開發時最頻繁的回饋。

### 26.2 Testing Library 元件與整合測試

- 在測試環境渲染 React 元件，依使用者可見的文字、Label、角色及操作測試，不依賴元件內部實作細節。
- 測試五步表單、資料保留、動態欄位、參與者操作、老師搜尋、附件驗證、錯誤聚焦、Dialog、簽名空白驗證、角色路由及審核頁籤。
- 加入 MSW 作為測試依賴，攔截前端 API 請求並模擬成功、欄位錯誤、權限、狀態衝突及伺服器錯誤，不修改真正資料庫。

### 26.3 Playwright 端對端測試

- 使用真正瀏覽器操作完整流程，驗證路由、表單、附件、Dialog、響應式畫面及跨頁狀態。
- 關鍵案例包含四種申請送件、競賽共享點數、老師待簽連結與簽名、老師拒絕、補件與重新簽名、承辦人調整及核准、多人操作 `409`、公開點數查詢及管理員唯讀權限。
- 開發前期可使用可控制的模擬 API；前後端整合後，重要完整流程必須連接後端測試環境及專用測試資料庫。
- 日常提交執行 Vitest、Testing Library 與 Chromium 關鍵 E2E；Firefox、WebKit 完整 E2E 在合併前、排程或發布前執行。
- 優先保證點數、Payload、權限與狀態轉移等高風險核心規則，不以單一整體覆蓋率數字取代有效案例。
