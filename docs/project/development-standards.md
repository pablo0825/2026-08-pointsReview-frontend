# 點數審核系統－開發與品質基準

- 文件狀態：第一版基準
- 最後更新：2026-08-13
- 相關文件：[前端架構](frontend-architecture.md)、[測試策略](testing-strategy.md)
- 整理來源：[初版前端實作計畫（封存）](../archive/initial-implementation-plan.md)

## 1. 開發原則

- 以可操作的垂直功能切片開發，不預先建立大量尚未使用的抽象層。
- 每個功能切片應同時處理畫面、資料存取、錯誤狀態、無障礙及必要測試。
- 後端尚未完成的契約可以使用最終 Zod Schema 與 MSW 開發，但真實 API 尚未驗證前，不得視為串接完成。
- 第一版不實作已明確排除的功能，包括草稿、學生進度查詢、自助撤回、案件指派及核准後點數異動。
- 契約或需求變更時，先更新對應文件，再調整實作。

## 2. 共通品質要求

- 畫面應涵蓋 Loading、Empty、Error、Success 及權限不足狀態。
- 表單可定位到單一欄位的錯誤，應在該控制項下方顯示文字訊息，並以紅色邊框及 `aria-invalid` 標示控制項；不得只靠顏色傳達錯誤，也不在頁面頂端重複列出同一批欄位錯誤。
- 跨欄位或集合規則應在最接近的相關區塊顯示；無法定位的表單錯誤、網路錯誤與系統錯誤才使用頁面內提示區塊，不使用瀏覽器原生 `alert()` 呈現一般錯誤。
- 驗證失敗時應合理移動焦點至第一個可操作錯誤欄位；錯誤文字與控制項須建立可被輔助科技辨識的關聯。
- 功能至少驗證 360px 寬度、鍵盤操作及基本螢幕閱讀器行為。
- 點數計算與比較使用整數最小單位，避免浮點數誤差。
- API Response 應經過 Zod 驗證；不得以不可靠的本機預設值取代必要的公開規則。
- 前端不得將 Session Token、簽名、附件或學生個資寫入未經允許的儲存空間或 Log。
- 測試層級與工具分工遵循[測試策略](testing-strategy.md)。

## 3. Tailwind CSS 使用規範

- 優先使用既有 theme token 與標準 utility；可由既有尺度表達時，不使用 arbitrary values。
- 重複出現的專案設計值應提升為 theme token，不在不同元件重複硬編碼。
- 不因 class 組合相似就過早建立抽象；只有具共同語意與行為的 UI 才封裝為共用元件。
- 自訂 CSS 必須保留在負責該行為的 Feature 或元件附近，不累積成大型全域樣式表。
- Tailwind utilities 不取代語意 HTML、可見焦點、色彩對比、鍵盤操作、觸控尺寸與 360px 響應式要求。
- 自動化測試以行為、可存取名稱及實際版面結果為主，不直接綁定完整 utility class 字串。

## 4. Definition of Done

每個功能必須同時符合以下條件，才可標記為完成：

- 功能行為已符合 Spec 與 API 契約。
- Loading、Empty、Error、Success 及權限狀態已處理。
- 360px、鍵盤操作及基本螢幕閱讀器行為已檢查。
- 沒有將個資、Token、附件或簽名寫入不允許的儲存空間或 Log。
- 必要的單元測試與元件測試已完成，關鍵使用者流程具備 Playwright 測試。
- Typecheck、Lint、Test 及 Production Build 全部通過。
- 契約或行為改變時，相關專案文件、Spec 及後端同步清單已更新。
- Spec 中的驗收條件已逐項確認。

## 5. Commit 策略

- 使用 Conventional Commits。
- 每個 Commit 保持單一、可說明且可審查的目的。
- 文件、基礎架構與功能實作原則上分開提交。
- 不將自動格式化產生的大量無關修改混入功能 Commit。
- 不在功能 Commit 中直接改寫既有需求決策；需求變更應先更新文件。
- 一個功能或階段可以拆成多個原子 Commit，不要求集中在單一 Commit。
