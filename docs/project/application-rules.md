# 點數審核系統－申請規則

- 文件狀態：第一版基準
- 最後更新：2026-08-16
- 相關文件：[產品需求](product-requirements.md)、[流程與權限](workflows-and-permissions.md)

## 1. 共用資料規則

### 1.1 申請類型

| API 值 | 中文名稱 | 人數 |
| --- | --- | ---: |
| `competition` | 競賽申請 | 1–10 |
| `project_participation` | 參與計畫申請 | 1 |
| `certificate` | 證照申請 | 1 |
| `exhibition` | 展覽申請 | 1–15 |

`exhibition` 同時涵蓋校內與校外展覽。舊值 `external_exhibition` 不再使用。

表列人數是第一版固定限制，不由公開 API 取得，也不提供管理員修改。參與人數規則管理與版本化延後至第二版。

### 1.2 學年度、年級與班級

- `academicYear` 為共用字串，送件時複製到每位參與者。
- 第一版依 Asia/Taipei 當日自動計算目前學年度，以 8 月 1 日為分界，不提供歷史學年度選擇器。
- 競賽申請不在表單與確認頁顯示學年度，但送件時仍將系統計算值複製到每位參與者；其他申請類型的顯示方式由各自 Slice 定義。
- 已知限制是學生無法補登歷史學年度案件；後續若校務規則允許補登，再另行定義可選範圍及適用規則。
- 年級：`1..4` 為大一至大四、`5..6` 為碩一至碩二。
- 班級：`1..5` 為甲班至戊班。
- 碩一、碩二班級預設甲班，但第一版仍允許選至戊班。

### 1.3 參與者與申請人

- 參與者至少一人，並遵守 1.1 的第一版固定人數限制。
- 每份申請只能有一位 `isApplicant = true`。
- 被指定者的 `studentName` 必須等於 `applicant.name`。
- 除競賽申請外，初始建立一位參與者並指定為申請人；競賽申請初始建立一位 `isApplicant = false` 的參與者，必須由使用者明確指定申請人。
- `applicant.name` 直接取指定參與者 trim 後的 `studentName`，不重複輸入。
- 競賽申請選定申請人前隱藏 Email 與電話；選定後在該參與者卡片的學籍欄位下方展開「申請人聯絡資料」。
- 競賽申請未指定申請人時不得離開參與者資料步驟，顯示「請先選擇一位參與者作為申請人。」並聚焦第一個「設為申請人」按鈕；指定後立即清除錯誤並展開聯絡資料。
- 更換申請人前先確認；更換後改用新申請人的姓名並清除 Email、電話，要求重新輸入聯絡資料。
- 已選定的申請人顯示「目前申請人」且不提供取消操作；目前申請人不可直接刪除，必須先指定其他參與者。競賽申請即使只剩一位參與者，仍須由使用者明確指定；其他申請類型維持初始申請人身分。
- `studentNumber` 的正式值為 trim 後轉成大寫的字串；正式送件、補件、後端驗證與儲存皆使用相同正規化規則。
- 同一 request 不得包含正規化後重複的 `studentNumber`。
- `requestedPoints` 與 `approvedPoints` 使用兩位小數字串。
- 所有核定點數必須大於 0 且符合類型規則。

## 2. 競賽申請

### 2.1 顯示名稱與獎項

競賽等級的 API 值與前端中文名稱如下：

| API 值 | 中文名稱 |
| --- | --- |
| `international_integrated` | 國際性整合型競賽 |
| `international_non_integrated` | 國際性非整合型競賽 |
| `national_integrated` | 全國性整合型競賽 |
| `national_non_integrated` | 全國性非整合型競賽 |
| `other` | 其他 |

獎項的 API 值與前端中文名稱如下：

| API 值 | 中文名稱 |
| --- | --- |
| `participation` | 參賽 |
| `finalist` | 入圍 |
| `honorable_mention` | 佳作 |
| `third_place` | 第三名 |
| `second_place` | 第二名 |
| `first_place` | 第一名 |

第一版只接受：

- `participation`
- `finalist`
- `honorable_mention`
- `third_place`
- `second_place`
- `first_place`

第一版不接受 `other_award`。未來若開放，必須先建立可套用的點數規則。

### 2.2 分配方式

`per_person`：

- 每位參與者取得規則固定點數。
- 前端自動帶入並設為唯讀。
- 人數異動時重新計算總點數。
- 畫面顯示「每人固定點數」，並說明每位參與者固定取得規則所列點數且不可自行修改。

`shared_total`：

- 規則點數是團隊可分配總點數。
- 不論一人或多人，每位參與者初始點數皆為 0.00，由申請人逐人分配，不自動平均或預先分配。
- 每人至少 0.5 點，且所有點數皆為 0.5 的倍數。
- 合計必須精確等於規則總點數。
- 實際人數上限為 `MIN(類型人數上限, FLOOR(總點數 / 0.5))`。
- 新增參與者時保留既有分配，新參與者帶入 0.00 點。
- 移除參與者時，移除者點數回到未分配額。
- 合計尚未平衡時不得送件。
- 參與者清單上方顯示團隊總點數、已分配點數與剩餘點數；第一版不固定於捲動畫面。
- 每位參與者提供明確的「−」與「＋」按鈕，每次調整 0.50 點，並保留可手動輸入的點數欄位；隱藏瀏覽器原生數字上下箭頭。
- 點數為 0.00 時停用「−」；剩餘點數不足 0.50 時停用會讓總和超過規則總點數的「＋」。手動輸入仍須通過最低值、倍數與總和驗證。
- 畫面顯示「團隊總點數分配」，並說明完成分配時每人至少 0.5 點且合計必須等於規則總點數。

學生切換競賽等級或獎項時保留參與者名單，但不得沿用舊規則的點數：

- 新規則為 `per_person` 時，每位參與者自動改為新規則的固定點數。
- 新規則為 `shared_total` 時，每位參與者皆重設為 0.00 點，再由學生重新分配。

### 2.3 其他驗證

- 競賽日期代表競賽完成或結果公布日期，必填且不得晚於台北時區的今天；不設定最早日期，歷史日期仍可申請。
- 前端從公開有效規則 API 取得 `competitionLevel`、`award`、`allocationMethod` 與 `points`，不得使用本機預設值替代。
- 找不到有效規則時不得送件。
- 正常填表期間只使用進入頁面時取得的規則，不因切換選項、步驟、參與者或點數而重複查詢。
- 送件時若後端判定規則已失效或點數不符合最新規則，前端保留其他資料、返回競賽內容步驟並要求使用者手動重新載入規則。
- 重新載入後若原競賽等級與獎項組合仍存在，保留選擇並依新規則重設點數；若組合已不存在，清除失效選擇並要求重新選擇。

## 3. 參與計畫申請

- 一份申請只能包含一個計畫及一位參與者，該參與者必須是申請人。
- `projectName` 必填，後端 trim 後不可為空，最長 255 字元，不限制一般字元。
- `principalInvestigator` 必填，後端 trim 後不可為空，最長 100 字元，不限制一般字元。
- `workDescription` 必填，後端 trim 後不可為空，最長 1,000 字元，可包含換行與一般符號。
- 每筆薪資包含 `salaryMonth` 與 `salaryAmount`。
- 每份申請至少一筆、最多 12 筆薪資明細，同一申請內月份不得重複。
- 月份只能是台北時區的當月或過去月份；API 使用該月份第一天，例如 `2026-08-01`。
- 金額以新臺幣元計，必須為 1～50,000 的整數；12 個月份的總額上限自然為 600,000 元。
- 後端目前先加總所有月份，再依有效規則計算：`FLOOR(totalSalary / 1000) * 0.5`；正式資格以換算點數是否至少為 0.50 判斷。
- 前端不自行實作換算公式，也不硬編碼總薪資門檻；使用者明確按下「試算點數」後，以 `POST /public/point-estimates/project-participation` 回傳的 `estimatedPoints` 與 `isEligible` 為準。
- 試算點數只供唯讀顯示，不提供申請人修改；任何薪資月份或金額異動都使既有試算失效，必須重新試算。
- `isEligible: false` 是成功試算結果，前端顯示未達申請門檻並禁止正式送件；正式送件仍由後端依送件當下的有效規則重新計算及覆寫點數。
- 學年度依共用規則動態計算，參與計畫表單與確認頁不顯示，但正式 payload 仍將系統值放入唯一參與者的 `academicYear`。
- 不同計畫不得合併薪資，必須分開申請。

## 4. 證照申請

- 一份申請只有一位參與者，且該參與者必須是申請人。
- 必填證照名稱、發照單位、證照編號與證照日期。
- 證照日期不得晚於台北時區的今天。
- 每張證照點數由有效規則自動設定，申請人與承辦人不得自由修改。
- 每位學生在學期間的證照累積上限由有效規則決定；超過時整筆不得核准，不做部分核准。
- 同一學生不得重複申請相同證照，暫以正規化後的 `studentNumber + certificateNumber` 判斷。
- 已有審核中、補件中或已核准申請時阻擋重複申請。
- 先前申請已因申請人要求結束或最終不核准時允許重新申請；第一版以 `rejected` 的終止原因判斷，正式 `withdrawn` 狀態列入第二版。

## 5. 展覽申請

### 5.1 類型與點數

| 展覽類型 | 中文名稱 | 每人允許點數 |
| --- | --- | --- |
| `fan_work` | 同人作品 | `0.50`、`1.00` |
| `project_work` | 專題作品 | `1.00`、`2.00` |

- 不接受端點之間的任意小數，例如 `0.75` 無效。
- 公開規則 API 使用 `allowedPointsPerPerson` 回傳兩位小數字串陣列。
- 前端使用單選或下拉選單，不提供自由輸入。
- 管理端規則 API 可保留最小值與最大值，由後端轉換為公開端點選項。
- 正式送件及核准仍由後端重新查詢規則並只接受端點值。

### 5.2 展覽資料

- 必填作品名稱、展覽名稱、主辦單位、場地、開始日期及結束日期。
- 選擇展覽名稱 `other` 時，其他名稱必填；否則必須為 `null`。
- 結束日期不得早於開始日期。
- 只能在展覽結束後申請，結束日期不得晚於台北時區的今天。

## 6. 申請點數與核定點數

- `requestedPoints` 保留學生原始申請值。
- `approvedPoints` 保存承辦人最終核定值。
- 核准後只有 `approvedPoints` 寫入不可直接修改的點數流水帳。
- 核定值必須大於 0，不建立零點流水帳。
- 競賽：承辦人可修正競賽等級，再依規則核定；不可任意輸入規則外點數。
- 展覽：只能從 `allowedPointsPerPerson` 核定。
- 參與計畫：不得直接修改計算值，資料有誤應要求補件。
- 證照：固定規則點數，不允許部分核准。
- 任何核定資料或點數調整都必須填寫原因；沒有調整時原因可為 `null`。

## 7. 附件規則

### 7.1 技術限制

- 格式：PDF、JPEG、PNG。
- 前端先以副檔名與 `File.type` 提示；後端同時檢查副檔名、multipart MIME type 與實際內容，`.jpg` 與 `.jpeg` 都接受。
- 每檔最大 5,242,880 bytes（`5 * 1024 * 1024`），每份申請最多 10 檔；大小限制是單檔而非附件合計。
- metadata 與 multipart 檔案透過唯一 `clientFileKey` 一一對應。
- `clientFileKey` 長度 1～80，只能包含英文字母、數字、底線與連字號，建議以前端 `crypto.randomUUID()` 產生；同一 request 不可重複，multipart 名稱固定為 `attachments[{clientFileKey}]`。
- `attachmentType` 必填；`attachmentTypeOther` 只在 `other` 時必填。
- `attachmentTypeOther` trim 後不可為空且最長 100 字元；切換離開 `other` 時立即清除並固定傳 `null`。
- `description` 選填、trim 後最長 500 字元；空白統一傳 `null`。
- 後端允許相同內容以不同 Key 重複加入；前端以檔名、大小與 `lastModified` 提示可能重複，讓使用者取消或仍然加入，每一份都占附件名額。
- JPEG、PNG 提供縮圖／檢視，PDF 可在新分頁開啟；本機 Blob URL 必須在關閉、移除或元件卸載時釋放。
- 刪除附件時一併移除檔案、metadata 與 Key；替換檔案保留分類、其他名稱與說明，但產生新 Key，替換檔案無效時保留原附件。

### 7.2 最低要求

| 申請類型 | 最低附件 |
| --- | --- |
| 競賽 | `participation_proof` 或 `finalist_or_award_certificate` 至少一份 |
| 參與計畫 | `salary_proof` 至少一份 |
| 證照 | `certificate_copy` 至少一份 |
| 展覽 | `exhibition_photo` 至少一份 |

第一版競賽仍採「`participation_proof` 或 `finalist_or_award_certificate` 至少一份」的後端規則；已知此分類式最低要求可能讓申請人不易判斷文件是否符合實際審查需求，後續可在取得更明確的文件政策後修訂，但不阻擋第一版。

### 7.3 前端可選分類

- 競賽：競賽辦法、海報、官網截圖、公文、參賽證明、入圍或獎狀、其他。
- 參與計畫：薪資證明、公文、其他。
- 證照：證照影本、其他。
- 展覽：展覽照片、展覽海報、公文、其他。

## 8. 規則適用與版本

- 點數規則以首次送件時間為適用日期，既有申請保存實際使用的點數規則 ID，後續不受新點數規則影響。
- 前端公開點數規則僅用於顯示與即時驗證，不能作為可信任資料。
- 第一版人數限制固定為 1.1 的數值，不建立人數規則 ID、有效期間或版本。
- 前端表單提供即時人數驗證，正式送件、補件與核准仍由後端依相同固定限制重新驗證。
- 第二版可再評估參與人數規則管理、版本化與公開 API；啟用前須另行定義契約與既有申請的適用方式。
- 補件不能改變申請類型或指導老師。
- 補件修改規則 Key 時，後端仍以首次送件時間選取當時適用的歷史規則。
