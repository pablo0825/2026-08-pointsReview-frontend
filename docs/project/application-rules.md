# 點數審核系統－申請規則

- 文件狀態：第一版基準
- 最後更新：2026-08-09
- 相關文件：[產品需求](product-requirements.md)、[流程與權限](workflows-and-permissions.md)

## 1. 共用資料規則

### 1.1 申請類型

| API 值 | 中文名稱 | 人數 |
| --- | --- | ---: |
| `competition` | 競賽申請 | 1–10 |
| `project_participation` | 參與計畫申請 | 1 |
| `certificate` | 證照申請 | 1 |
| `exhibition` | 展覽申請 | 1–15 |

`exhibition` 同時涵蓋校內與校外展覽。舊值 `external_exhibition` 不再使用。

### 1.2 學年度、年級與班級

- `academicYear` 為共用字串，送件時複製到每位參與者。
- 年級：`1..4` 為大一至大四、`5..6` 為碩一至碩二。
- 班級：`1..5` 為甲班至戊班。
- 碩一、碩二班級預設甲班，但第一版仍允許選至戊班。

### 1.3 參與者與申請人

- 參與者至少一人，實際上下限由首次送件時有效的人數規則決定。
- 每份申請只能有一位 `isApplicant = true`。
- 被指定者的 `studentName` 必須等於 `applicant.name`。
- 同一 request 不得包含重複 `studentNumber`。
- `requestedPoints` 與 `approvedPoints` 使用兩位小數字串。
- 所有核定點數必須大於 0 且符合類型規則。

## 2. 競賽申請

### 2.1 獎項

第一版只接受：

- `participation`
- `finalist`
- `honorable_mention`
- `third_place`
- `second_place`
- `first_place`

第一版不接受 `other_award`。未來若開放，必須先建立可套用的點數規則。

### 2.2 分配方式

`per_person`：

- 每位參與者取得規則固定點數。
- 前端自動帶入並設為唯讀。
- 人數異動時重新計算總點數。

`shared_total`：

- 規則點數是團隊可分配總點數。
- 一人時自動取得全部點數。
- 多人時由申請人逐人分配，不自動平均。
- 每人至少 0.5 點，且所有點數皆為 0.5 的倍數。
- 合計必須精確等於規則總點數。
- 實際人數上限為 `MIN(類型人數上限, FLOOR(總點數 / 0.5))`。
- 新增參與者時保留既有分配，新參與者先帶入 0.5 點。
- 移除參與者時，移除者點數回到未分配額。
- 合計尚未平衡時不得送件。

### 2.3 其他驗證

- 競賽日期代表競賽完成或結果公布日期，必填且不得晚於台北時區的今天。
- 前端從公開有效規則 API 取得 `competitionLevel`、`award`、`allocationMethod` 與 `points`，不得使用本機預設值替代。
- 找不到有效規則時不得送件。

## 3. 參與計畫申請

- 一份申請只能包含一個計畫及一位參與者，該參與者必須是申請人。
- 必填計畫名稱、計畫主持人、工作概述及至少一筆薪資明細。
- 每筆薪資包含 `salaryMonth` 與 `salaryAmount`。
- 同一申請內月份不得重複。
- 月份只能是台北時區的當月或過去月份；API 使用該月份第一天，例如 `2026-08-01`。
- 金額以新臺幣元計，必須為大於 0 的整數。
- 系統先加總所有月份，再依有效規則計算：`FLOOR(totalSalary / 1000) * 0.5`。
- 未滿 1,000 元時預估為 0 點並禁止送件。
- 前端預估只供顯示，正式送件由後端重新計算。
- 不同計畫不得合併薪資，必須分開申請。

## 4. 證照申請

- 一份申請只有一位參與者，且該參與者必須是申請人。
- 必填證照名稱、發照單位、證照編號與證照日期。
- 證照日期不得晚於台北時區的今天。
- 每張證照點數由有效規則自動設定，申請人與承辦人不得自由修改。
- 每位學生在學期間的證照累積上限由有效規則決定；超過時整筆不得核准，不做部分核准。
- 同一學生不得重複申請相同證照，暫以 `studentNumber + certificateNumber` 判斷。
- 已有審核中、補件中或已核准申請時阻擋重複申請。
- 先前申請已因申請人要求結束或最終不核准時允許重新申請；第一版以 `rejected` 的終止原因判斷，正式 `withdrawn` 狀態列入第二版。

## 5. 展覽申請

### 5.1 類型與點數

| 展覽類型 | 中文名稱 | 每人允許點數 |
| --- | --- | --- |
| `fan_work` | 同人作品 | `0.50`、`1.00` |
| `project_work` | 專題作品 | `1.00`、`2.00` |

- 不接受端點之間的任意小數，例如 `0.75` 無效。
- 公開規則 API 使用 `allowedPointsPerPerson` 回傳兩位小數字串陣列。
- 前端使用單選或下拉選單，不提供自由輸入。
- 管理端規則 API 可保留最小值與最大值，由後端轉換為公開端點選項。
- 正式送件及核准仍由後端重新查詢規則並只接受端點值。

### 5.2 展覽資料

- 必填作品名稱、展覽名稱、主辦單位、場地、開始日期及結束日期。
- 選擇展覽名稱 `other` 時，其他名稱必填；否則必須為 `null`。
- 結束日期不得早於開始日期。
- 只能在展覽結束後申請，結束日期不得晚於台北時區的今天。

## 6. 申請點數與核定點數

- `requestedPoints` 保留學生原始申請值。
- `approvedPoints` 保存承辦人最終核定值。
- 核准後只有 `approvedPoints` 寫入不可直接修改的點數流水帳。
- 核定值必須大於 0，不建立零點流水帳。
- 競賽：承辦人可修正競賽等級，再依規則核定；不可任意輸入規則外點數。
- 展覽：只能從 `allowedPointsPerPerson` 核定。
- 參與計畫：不得直接修改計算值，資料有誤應要求補件。
- 證照：固定規則點數，不允許部分核准。
- 任何核定資料或點數調整都必須填寫原因；沒有調整時原因可為 `null`。

## 7. 附件規則

### 7.1 技術限制

- 格式：PDF、JPEG、PNG。
- 每檔最大 5 MB，每份申請最多 10 檔。
- metadata 與 multipart 檔案透過唯一 `clientFileKey` 一一對應。
- `attachmentType` 必填；`attachmentTypeOther` 只在 `other` 時必填。
- `description` 選填。

### 7.2 最低要求

| 申請類型 | 最低附件 |
| --- | --- |
| 競賽 | `participation_proof` 或 `finalist_or_award_certificate` 至少一份 |
| 參與計畫 | `salary_proof` 至少一份 |
| 證照 | `certificate_copy` 至少一份 |
| 展覽 | `exhibition_photo` 至少一份 |

### 7.3 前端可選分類

- 競賽：競賽辦法、海報、官網截圖、公文、參賽證明、入圍或獎狀、其他。
- 參與計畫：薪資證明、公文、其他。
- 證照：證照影本、其他。
- 展覽：展覽照片、展覽海報、公文、其他。

## 8. 規則適用與版本

- 人數及點數規則以首次送件時間為適用日期。
- 前端公開規則僅用於顯示與即時驗證，不能作為可信任資料。
- 正式送件、補件與核准皆由後端重新驗證。
- 既有申請保存實際使用的規則 ID，後續不受新規則影響。
- 補件不能改變申請類型或指導老師。
- 補件修改規則 Key 時，後端仍以首次送件時間選取當時適用的歷史規則。
