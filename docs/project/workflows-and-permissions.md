# 點數審核系統－流程與權限規格

- 文件狀態：第一版基準
- 最後更新：2026-08-11
- 相關文件：[產品需求](product-requirements.md)、[申請規則](application-rules.md)

## 1. 申請狀態

| 狀態 | 說明 | 終止狀態 |
| --- | --- | --- |
| `pending_advisor` | 等待指導老師簽名或拒絕 | 否 |
| `under_review` | 老師已同意，等待承辦人審核 | 否 |
| `needs_revision` | 等待學生透過補件連結重新提交 | 否 |
| `approved` | 已核准並建立點數流水帳 | 是 |
| `rejected` | 已拒絕、逾期作廢或依申請人要求結束 | 是 |

進入 `approved` 或 `rejected` 時必須寫入 `closedAt`；其他狀態的 `closedAt` 必須為 `null`。

## 2. 狀態轉移

```text
建立申請 -> pending_advisor

pending_advisor -> under_review   老師簽名同意
pending_advisor -> rejected       老師拒絕或簽核逾期

under_review -> needs_revision    承辦人要求補件
under_review -> approved          承辦人核准
under_review -> rejected          承辦人最終不核准

needs_revision -> pending_advisor 學生完成補件並建立新版本
needs_revision -> rejected        補件逾期、承辦人最終不核准或依申請人要求結束
```

- 第一版沒有 `draft` 或 `withdrawn` 狀態。
- 終止狀態不得恢復、修改或補件。
- 所有寫入操作都由後端在 Transaction 內重新驗證狀態與目前版本。

## 3. 初次送件

1. 學生完成五步公開表單。
2. 前端送出申請主資料、參與者、類型資料、附件 metadata 與檔案。
3. 後端驗證第一版固定人數限制及有效點數規則，建立第 1 版快照。
4. 申請進入 `pending_advisor`，寫入老师簽核期限。
5. 建立老師簽核通知與三次提醒任務。
6. 成功頁顯示 `publicId`；第一版學生之後只透過 Email 接收狀態通知。

## 4. 指導老師簽核

### 4.1 同意

1. 老師從 Email 連結進入；未登入時先導向共用登入頁，成功後返回原申請。
2. 老師只能讀取 `advisorId` 對應自己的申請。
3. 老師檢視目前版本、參與者、類型資料、附件與歷史。
4. 老師在 Dialog 內手寫簽名，前端送出 PNG 及 `confirmVersionNumber`。
5. 後端驗證期限、狀態、資料所有權與版本，建立不可覆蓋的簽名紀錄。
6. 申請進入 `under_review`。

### 4.2 簽名限制

- 簽名只能在頁面手寫，不允許上傳既有圖片。
- PNG 最大 1 MB、1600 × 800。
- 最終簽名由後端合成「僅供本次點數審核申請使用」浮水印，以及申請編號、版本與簽署時間。
- 前端不持久保存原始簽名筆跡。
- 簽名檔只能透過具權限私有 API 讀取。

### 4.3 拒絕

- 老師拒絕不需要簽名，但原因必填。
- 送出前清楚提示操作會永久結束申請。
- 申請轉為 `rejected`，通知申請人。
- 老師第一版不能要求補件；需要修改時學生須重新申請。

### 4.4 期限

- 期限為進入 `pending_advisor` 後 168 小時。
- 立即寄送通知，期限前 72、24、4 小時提醒。
- 逾期由系統轉為 `rejected`。
- 第一版不延長老師簽核期限。

## 5. 承辦人審核

### 5.1 共用案件池

- 所有啟用承辦人可查看全部案件。
- 第一版不認領、指派或依系所隔離。
- 多位承辦人可同時閱讀；寫入時後端以短 Transaction 與資料列鎖避免重複操作。
- 第二位寫入者若發現狀態已變，回傳 `409`；前端重新載入最新案件。

### 5.2 要求補件

1. 承辦人對 `under_review` 案件填寫補件原因。
2. 申請進入 `needs_revision`，後端產生限時 Token 並寄送補件連結。
3. 學生可修改申請，但不能改變 `applicationType` 或 `advisorId`。
4. 重新提交後建立新版本，不覆蓋舊版本。
5. 舊簽名標記失效，申請回到 `pending_advisor`。
6. 原老師必須重新檢視新版本並簽名。
7. 老師同意後再次進入 `under_review`。

承辦人可多次要求補件，每次都建立新 Token、版本與歷史事件。

### 5.3 補件期限

- 預設期限為 7 天，到期前 24 小時提醒。
- 在 Token 仍有效時，承辦人可設定更晚期限並填寫原因。
- 延長不更換 Token；重新安排尚未寄出的提醒。
- 到期未提交時由系統轉為 `rejected`。
- `needs_revision` 可由承辦人填寫原因後提前最終不核准。
- `needs_revision` 不可直接核准或再次要求補件。

### 5.4 核准

- 只允許 `under_review` 且具有目前版本有效老師簽名的案件。
- 無調整時沿用申請值，調整原因為 `null`。
- 有任何核定資料或點數調整時，須一次傳送完整核定參與者、核定總點數及非空白原因。
- 核定值必須符合類型規則且大於 0。
- 後端在同一 Transaction 更新狀態、保存核定值與操作、建立所有 `award` 流水帳及通知任務。
- 成功後進入 `approved`，通知申請人、老師與目前主任。

### 5.5 最終不核准

- `under_review` 或 `needs_revision` 可最終不核准。
- 原因必填，送出前提示不可恢復。
- 申請進入 `rejected`，不建立點數。
- 可修正案件應使用要求補件，不應直接不核准。

## 6. 學生送件後操作

- 第一版沒有主動進度查詢頁。
- 學生只能在收到補件通知後，透過限時 Token 修改申請。
- 第一版沒有自助撤回。
- 待老師簽名時，學生聯絡老師，由老師以「申請人要求撤回」等原因拒絕。
- 已進入承辦階段時，學生聯絡承辦人，由承辦人最終不核准。
- 第二版再評估唯讀查詢 Token 與正式 `withdrawn` 狀態。

## 8. 登入與 Session

- 後台角色共用 `/login`，使用 Email 與密碼。
- 成功後後端設定 HttpOnly Session Cookie。
- 前端透過 `/auth/me` 取得角色與權限。
- State-changing API 使用與 Session 綁定的 CSRF Token。
- 401 清除登入快取並回到登入頁；403 顯示權限不足。
- 待簽深連結登入後返回原申請。

## 9. 審核歷史與稽核

- `application_review_actions` 保存所有申請流程事件並在詳情頁顯示時間軸。
- 老師只看自己案件；承辦人看全部審核案件；管理員唯讀看全部。
- `audit_logs` 保存帳號、老師、主任、規則與敏感檔案查看操作。
- 第一版後端寫入 `audit_logs`，前端不提供稽核查詢頁。

## 10. 併發與版本安全

- 前端操作權限只是介面提示，後端必須重新驗證角色、資料所有權、狀態與版本。
- 老師簽名綁定 `confirmVersionNumber`。
- 承辦人核准綁定目前版本，寫入前鎖定案件。
- 409 時前端不得重送舊資料，必須重新取得最新案件。
- 所有舊版本、失效簽名、補件原因、期限變更及審核操作皆保留。
