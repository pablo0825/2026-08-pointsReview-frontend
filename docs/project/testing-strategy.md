# 點數審核系統－前端測試策略

- 文件狀態：第一版基準
- 最後更新：2026-08-13
- 相關文件：[產品需求](product-requirements.md)、[前端架構](frontend-architecture.md)

## 1. 測試目標

- 優先保護點數計算、資料轉換、權限與狀態轉移。
- 以最便宜且最接近問題來源的測試層處理案例。
- 不依賴單一覆蓋率數字判斷品質。
- 前端可在後端未啟動時測試各種 API 成功與失敗畫面；整合完成後仍須以真正後端測試核心流程。

## 2. 測試分層

| 層級 | 工具 | 測試內容 | 速度 |
| --- | --- | --- | --- |
| 單元 | Vitest | 純函式、Schema、Mapper、點數與日期 | 快 |
| 元件／整合 | Vitest + Testing Library + MSW | React 畫面、互動、API 狀態 | 中 |
| 端對端 | Playwright | 真正瀏覽器與完整角色流程 | 慢 |

## 3. Vitest 單元測試

### 3.1 點數

- 兩位小數字串與整數最小單位雙向轉換。
- 無效格式、負數、零與超過安全範圍。
- 0.5 倍數判斷。
- `per_person` 人數異動後總點數。
- `shared_total` 每人大於 0、總和精確、動態人數上限、新增與移除行為。
- 參與計畫先加總再 `FLOOR` 換點，未滿 1,000 元不可送件。
- 展覽離散端點。

### 3.2 表單與 Mapper

- 申請人必須是參與者且只有一位。
- 學年度複製到所有參與者。
- 同一 request 學號不可重複。
- 四種 Form Model 正確轉為 Discriminated API Payload。
- 附件 metadata 與 File 一一對應。
- 補件保留附件 ID 與新增附件的組合。

### 3.3 日期與選項

- 台灣目前學年度 8 月 1 日分界。
- 未來競賽、證照、展覽日期無效。
- 薪資月份不可未來或重複。
- 年級、班級與老師職稱對照。
- 公開點數查詢條件。

### 3.4 錯誤

- API `fields[].path` 對應 React Hook Form Path。
- 401、403、404、409、422、429 與 5xx 行為分類。
- 不可辨識 Error 不暴露原始技術資訊。

## 4. Testing Library 與 MSW

### 4.1 公開申請

- 四個申請類型連結導向正確路由。
- 五步表單的下一步驗證、上一步保留與預覽返回。
- 離開未送出表單時警告。
- 多人新增、移除、重複學號及申請人指定。
- 共享點數顯示已分配與剩餘點數。
- 老師搜尋姓名、職稱、系所；不顯示主任。
- 附件分類、其他類型、數量、大小及最低要求。
- 422 欄位錯誤返回正確步驟並聚焦。
- 重複點擊只開始一次邏輯送件；`Idempotency-Key` 必須是 UUID v4。
- 結果不確定後以相同 Key、payload 與附件快照重試，只建立一筆案件並重放相同 `201` 結果。
- 修改 payload 或附件後廢棄舊 Key，下一次送件產生新 Key；`409 idempotency_key_conflict` 不再沿用衝突 Key。
- Idempotent retry 與 `429 rate_limited` 狀態可分別辨識，且 Mutation 不自動重試。
- 成功頁顯示申請編號。

### 4.2 老師

- 未登入深連結登入後返回原申請。
- 待簽列表截止時間排序與到期警示。
- 詳情只對目前版本提供操作。
- 簽名 Dialog 焦點、空白禁用、清除、關閉筆跡確認及送出狀態。
- 拒絕原因必填及不可恢復提示。
- 409 關閉 Dialog 並重新載入。

### 4.3 承辦人

- `under_review` 與 `needs_revision` 使用不同 API Query。
- 兩個頁籤各自保留分頁及篩選。
- 核定值與申請值比對，有調整時原因必填。
- 要求補件、延長、核准及不核准 Dialog。
- 補件中不顯示核准或再次補件。
- Mutation 成功後正確 invalidate 兩個 Queue 與歷史列表。

### 4.4 管理員與公開頁

- 管理員導覽及角色限制。
- 管理員申請詳情不顯示審核按鈕。
- 年度 Markdown 經 Sanitizer，不執行危險內容。
- 公開點數條件不足不呼叫 API。
- 遮罩資料與四類點數正確顯示。

## 5. MSW 規則

- Handler 以後端 Endpoint 分組，回傳資料先通過測試 Fixture Schema。
- 預設 Handler 只描述一般成功；個別測試覆寫錯誤或邊界。
- 測試結束後重設 Handler，禁止未處理 Request 靜默通過。
- Fixture 不使用真實姓名、Email、電話、簽名或附件。
- 契約改變時同步更新 Zod Schema、Handler 與 Contract Test。

## 6. Playwright 關鍵流程

1. 競賽 `per_person` 申請成功。
2. 競賽 `shared_total` 多人分配成功與總和錯誤阻擋。
3. 參與計畫多月薪資試算與送件。
4. 證照固定點數與附件送件。
5. 展覽離散點數與多人送件。
6. 老師從 Email 深連結登入、查看附件、手機手寫簽名。
7. 老師填寫原因拒絕。
8. 承辦人要求補件，學生重送，舊簽名失效，老師重新簽名。
9. 承辦人依規則調整並核准，公開點數頁出現遮罩結果。
10. 兩位承辦人同時操作，第二位收到 409 並看到最新狀態。
11. 補件延長、逾期及人工不核准。
12. 管理員可唯讀查看但不能審核。

## 7. 真實後端整合

- UI 開發前期的 Playwright 可攔截 API，快速驗證路由與互動。
- 核心驗收必須啟動後端測試環境及專用測試資料庫。
- 測試資料以 Seed／Factory 建立，不依賴共享人工資料。
- 每個測試可獨立執行並清理自己建立的資料。
- Email 使用測試收件匣或 Mail Sink，從實際通知取得老師／補件連結。
- 逾期流程使用可控時鐘或測試設定，不在測試中等待真實數天。

## 8. 執行節奏

開發中：

- Vitest Watch 執行相關單元與元件測試。

每次提交／PR：

- TypeScript 型別檢查。
- Lint。
- 全部 Vitest／Testing Library。
- Chromium 關鍵 Playwright。

合併前或排程：

- Firefox 與 WebKit 完整 Playwright。
- 無障礙掃描與 360px／手機簽名流程。
- 真實後端核心審核流程。

發布前：

- Production Build。
- 三瀏覽器 Smoke Test。
- 公開申請、老師簽名、承辦核准與公開點數完整串接。

## 9. 失敗判斷

- 不允許 Flaky Test 直接重跑後忽略；必須追蹤並修正原因。
- Screenshot、Trace、Video 只在失敗時保留，且測試資料不得包含真實個資。
- 因契約錯誤造成的 Zod Parse Failure 視為整合失敗，不以型別斷言繞過。
- 關鍵流程失敗時不得發布，即使整體覆蓋率達標。
